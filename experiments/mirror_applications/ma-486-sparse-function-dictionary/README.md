# MA-486 — Sparse dictionary Mirror function representation

Status: **FAIL** for Mirror-specific attribution (development screen; fresh sealed)

## H — Falsifiable hypothesis

For functions generated by three active atoms from one shared 32-atom matrix dictionary, sparse int8 codes will reproduce heldout outputs at RMSE <=0.01, use at most 80% of the complete dense-int8 dictionary payload bytes, and reduce decode operations in both seeds. Standard OMP will be used as the native sparse-code attribution control.

## T — What ran

Two frozen development worlds (48601, 48602), each with 192 functions, 128 train and 64 heldout, D=16, a shared dictionary of 32 orthonormal 16x16 matrix atoms, three active coefficients per function and 64 fixed queries. Compared independent matrices, dense float/int8 dictionary codes, sparse float/int8 codes obtained by three-step OMP, and exact native OMP controls. Every payload pays the full float32 dictionary; sparse IDs are stored as uint8; scales and metadata are included. OMP encode work is separated from decode/query work. Independent upper reproduces targets. Full serialization and output replay passed; tests 3 passed. Fresh seeds 48611–48613 remained sealed.

## D — Decision

**FAIL** for Mirror-specific attribution. Sparse int8 payload was 35,379 B versus 40,090 B dense int8 (11.8% smaller), missing the frozen <=0.80x storage gate. It reached the same int8-scale output error and reduced the decode operation proxy 90.6%, but its full OMP+decode+query proxy was 5.91M versus 7.34M for dense int8. Native OMP exactly aliases the sparse representation.

## Facts

- Sparse float: 36,851 B, RMSE <=1e-7, 1.0 distinct heldout code fraction. Dense float: 58,278 B, exact outputs.
- Sparse int8: 35,379 B, RMSE 0.0005681 / 0.0005628. Dense int8: 40,090 B, RMSE 0.0005681 / 0.0005628.
- All shared-dictionary methods pay its 32,768 float32 atom bytes plus schema/scales. Sparse int8 saves 4,711 B, but not the preregistered 8,018 B required for the 20% storage gate.
- Sparse decode proxy was 147,456 versus dense 1,572,864 operations. OMP encode proxy was 4,718,592 in both; query proxy was 1,048,576.
- Sparse/native OMP bytes, SHA256 and outputs matched exactly for float and int8 controls in both seeds. Verification replay difference was zero.

## Interpretations

Sparse coordinates lower decode work substantially and provide a modest actual-byte reduction over dense int8 on this aligned task. Paying for the large shared dictionary leaves the total payload close to the dense baseline. The observed sparse-coding gain is standard OMP behavior rather than a Mirror-specific improvement.

## C — Strongest counter-hypothesis

The float32 shared dictionary dominates payload; quantizing or factorizing that physical basis could improve sparse storage, but would affect all code methods and is a separate axis requiring its own controls. Sparse int8 may also incur larger OMP encode work in a realistic learned-dictionary deployment than this tiny synthetic CPU screen reveals.

## U — Still unknown

Natural tasks, learned dictionary formation, trained model quality, GPU latency and amortized dictionary update costs are untested. MA-487 will separately test learned LISTA code inference with matched sparse dictionary and OMP controls.
