# AGENTS.md

## Repository mission

This repository studies whether low-description Mirror/View coordinates can turn one physical parameter object into multiple useful logical functions, reducing physical duplication while preserving quality.

## Start here

Read `WORKER_START_HERE.md` before making research changes.

Then read `docs/phase2/MIRROR_PARAMETER_INTEGRATION_DOCTRINE.md` and `docs/phase2/MIRROR_PARAMETER_INTEGRATION_MATRIX.md`. The Mirror application program is centered on the extra low-description functional parameter `m`; new external methods are primarily targets/controls for inserting and stress-testing that parameter, not replacements for the Mirror question.

## Current active program

Work on one MA ID at a time. Follow `experiments/mirror_applications/EXPERIMENT_CONTRACT.md`.

## Non-negotiable evidence rules

- Storage claims use actual serialized inference bytes.
- Fresh/audit results do not tune hyperparameters.
- Fixed-update gains are not capacity proofs.
- Mirror-specific claims require a simpler non-Mirror shared/low-rank control.
- Preserve negative results and historical reports.
- Do not edit `third_party/nanoGPT/` to implement an experiment.
- Do not merge research branches into main unless explicitly requested.

## Historical context

SRM and TM reports are evidence, not the current task queue. Use them when referenced by the selected MA candidate.

## Output discipline

Every experiment needs a protocol, result table, verification record, and a scoped conclusion stating what is and is not established.


## Concurrent registry edits

Before adding a new MA candidate, re-read `IDEA_REGISTRY.csv` from the current branch and allocate IDs starting at **max existing MA ID + 1**. Never reserve an ID from memory or an older checkout. After writing, re-read the registry and verify zero duplicate IDs. If concurrent additions collide, preserve both hypotheses and renumber the later addition rather than deleting either one.
