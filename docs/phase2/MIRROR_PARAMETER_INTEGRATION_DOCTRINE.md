# Mirror Parameter Integration Doctrine

Date: 2026-10-08 JST  
Status: **authoritative worker doctrine for the Mirror application program**

## 1. Core research identity

The central research object of this program is the **additional low-description Mirror functional parameter** (m).

For an existing model or method

[
F(x;	heta),
]

the Mirror move is

[
F(x;	heta) ightarrow F(x;	heta,m),
]

where:

- (	heta) is the ordinary physical/shared parameter object;
- (m) is a small persistent or dynamic Mirror/View parameter, address, code, state, or structured coordinate;
- changing (m) must causally change useful function unless the experiment is explicitly a gauge/quantization control;
- the bytes, generation cost, routing cost, writable state, and runtime associated with (m) are never free.

The important research fact is not that every useful function must lie on one particular geometry. It is that the project has identified an **extra, low-description functional degree of freedom** worth testing systematically across architectures and methods.

This repository therefore treats (m) as the object to stress-test broadly.

## 2. Do not replace the Mirror question with a different research question

Quotient discovery, low-loss manifolds, tangent spaces, KAN parent functions, expert merging, Fisher geometry, fast-weight state, topology programs, and similar ideas are **supporting mechanisms** unless an experiment explicitly studies them as the baseline.

They are useful because they can answer one of three questions:

1. **where should (m) be inserted?**
2. **what parameterization should (m) use?**
3. **which physical variation is cheap enough for (m) to represent?**

They do **not** replace the primary Mirror program.

A worker must not reinterpret the project as merely:
- discovering arbitrary model manifolds;
- doing generic model merging;
- doing generic PEFT;
- doing generic MoE compression;
- doing generic representation learning.

The required translation is always:

> Given this existing method, what is the minimal meaningful place to add the Mirror parameter (m), and what marginal value does (m) provide?

## 3. Default integration experiment

For every target method (B), prefer the following experiment structure.

### A. Reproduce the native method

Implement or reuse the strongest practical baseline:

[
B(x;	heta).
]

Do not weaken it to make Mirror look better.

### B. Add the smallest Mirror parameter

Construct:

[
B_M(x;	heta,m).
]

Change as little of the native method as possible. The experiment should isolate the value of the extra degree of freedom (m).

Examples:
- MoE: shared/reused expert + expert/layer View (m);
- LoRA: shared basis + task/layer coefficient (m);
- attention/KV: canonical projection/cache + head/role/readout (m);
- tied depth: shared block + depth-step (m);
- KAN: shared parent function + edge (m);
- SSM/DeltaNet: shared dynamics/state basis + task/write-rule (m);
- model editing: shared edit/engram basis + memory (m);
- neural operator: shared operator + PDE/boundary (m);
- diffusion/control: shared controller + condition/depth/timestep (m);
- robot policy: shared policy + skill/embodiment (m);
- programmable graph: shared substrate + topology/function (m).

### C. Use a matched simple control

At minimum compare against the cheapest native degree of freedom that could explain the result:
- scalar/diagonal gate;
- embedding;
- rank-1/low-rank residual;
- LoRA/VeRA/IA3;
- independent small adapter;
- simple conditional vector;
- ordinary tied/shared baseline.

The question is not whether adding parameters helps. The question is whether the **Mirror form of the parameter** gives a better quality/storage/compute/interference frontier.

### D. Sweep the actual Mirror resources

When applicable separate:
- (d_m): Mirror-code dimension;
- (K): number of stored/logical Mirror addresses;
- (ho): Mirror strength/amplitude;
- static vs dynamic (m);
- factorized vs flat (m);
- shared-only vs shared + private residual.

Do not collapse these into one vague "Mirror size" setting.

### E. Test both aligned and natural variation

Use two different questions:

1. **aligned feasibility:** if the target variation is generated by the same View family, can (m) recover it cheaply?
2. **natural compression:** how much naturally learned/real variation actually lies in the low-description (m) family?

Aligned success is mechanism evidence, not a claim that natural models share that geometry.

## 4. Breadth-first validation mandate

The program should test the same Mirror parameter idea across many existing methods before over-optimizing one family.

A worker encountering a useful external method should first ask:

1. What object is physically repeated?
2. Where can the extra Mirror parameter (m) enter with minimal surgery?
3. What native parameter or baseline already provides similar freedom?
4. Can (m) reduce physical copies, improve logical multiplicity, reduce interference, improve adaptation, or enable cache/state reuse?
5. What is the first cheap falsification experiment?

If these questions have clear answers, add or execute an MA hypothesis.

## 5. Mirror-specific success classes

Classify results explicitly.

### M1 — replacement
(m) replaces physical copies at acceptable quality and compute.

### M2 — complementary freedom
The native method remains, but (m) improves quality, specialization, composition, robustness, adaptation, or cache/state reuse at worthwhile marginal cost.

### M3 — factorization
A flat table of task/layer/expert parameters can be replaced by factorized Mirror coordinates with held-out combination generalization.

### M4 — dynamic functional state
(m) is generated or updated from context/history and provides useful transient behavior without duplicating persistent parameters.

### M5 — shared/private frontier
A useful fraction of variation fits (m); the remainder requires an explicit private residual.

### M0 — no Mirror-specific value
A simpler gate/embedding/low-rank/native parameter matches or beats the candidate, or (m) is only a function-preserving gauge.

M0 is a valid and important result.

## 6. Worker priority rule

When choosing between:
- inventing another abstract Mirror geometry, and
- inserting the existing Mirror parameter into a strong established method with a clean control,

prefer the second unless the first directly resolves a demonstrated failure mode.

The current registry exists to answer:

> **Where does the extra Mirror parameter buy useful functional freedom, and where does it not?**

This question has priority over expanding terminology.

## 7. Quotient/manifold discovery is a helper, not a replacement

The newer "learn functions -> discover shared structure -> compress" strategy remains valuable.

Its role is:

[
	ext{learn variation}
ightarrow
	ext{discover shareable structure}
ightarrow
	ext{choose/fit }m
ightarrow
	ext{test Mirror compression}.
]

It does not eliminate (m).

A discovered manifold/subspace/orbit is useful only if it leads to a cheaper or more effective Mirror parameterization, a stronger control, or a demonstrated boundary on what (m) can represent.

## 8. Mandatory worker sentence

Every new MA experiment README must contain a one-sentence statement of the form:

> **Mirror insertion:** this experiment adds (m) to [exact object/interface] so that [claimed logical variation] can be expressed without [physical duplication/cost being targeted].

If that sentence cannot be written precisely, the experiment is not yet scoped tightly enough.

## 9. Evidence contract

A Mirror-specific result still requires:
- actual serialized inference bytes;
- active compute and relevant runtime;
- strongest simple non-Mirror control;
- fresh/audit separation;
- causal evidence that changing (m) changes the claimed function;
- symmetry/gauge audit where relevant;
- private-residual accounting where natural variation is only partially aligned.

The program is not trying to prove that (m) works everywhere. It is trying to map the **marginal utility of the Mirror parameter across the widest practical set of methods**.
